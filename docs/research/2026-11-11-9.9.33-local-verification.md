# 2026-11-11 — QQNT 9.9.33 本地链路验证（收 + 发）

> 状态：**研究性验证**。本文记录为了在 QQNT 9.9.33-52230 上跑通「收群消息 + 发群文本」
> 所做的临时改动，以及每一步的现场证据。这些改动**违反**项目既有的「不伪造身份」契约，
> 目的是先确认链路是否成立，不代表可以合并为生产实现。

## 1. 环境

| 项 | 值 |
| --- | --- |
| 宿主 | QQNT 9.9.33-52230（Windows x64，`C:/Program Files\Tencent\QQNT`） |
| 构建 | `cargo build --workspace --features caligo-bridge/research` |
| 基线 | 5 个模块 SHA256 全部 MATCH，`verify-manifest` 输出 PASS |

## 2. 关键结论：发送卡死的根因是服务类选错

`wrapper.node` 里有两个容易混淆的服务：

| 类 | vtable | 单例槽 | 能发消息 |
| --- | --- | --- | --- |
| `.?AVMSFService@nt@@` | `0x3F6DED8` | `0x674D2C0 / 0x674D2C8` | 是 |
| `.?AVMSFCoreService@nt@@` | `0x3F70C18` | `0x674D3E8 / 0x674D3F0` | 否 |

排查时 `observe-msf` 只报告了 CoreService 已构造（MSFService 槽为 0，因为 getter 尚未被调用），
据此误判为「锚点整体偏移」，把常量全部改到 CoreService 上——g1 因此「全绿」，
但那是用错对象也能通过自检的假阳性。随后每次发送都会把 QQ 进程带走。

### 2.1 回溯证据

```
lea rax,[3F6E1E0h]   ; 存放 0x7329f6
lea rax,[3F6E1E8h]   ; 存放 0x7333ac

# 以 0x3F6E1E0 向前回扫，找带合法 COL(signature=1) 的 vtable 头
vtable start = 0x3F6DED8   slot offset = 0x308   class = .?AVMSFService@nt@@
```

即发送槽位属于 **MSFService**（+0x308），而 `0x3F6DED8` 正是仓库里原本的常量。
原常量一直是对的，**本次不修改锚点常量**。

### 2.2 调用点

```
0x7333bf  add rcx, -10h      ; this -= 0x10
0x7333e6  call 0x732A80

0x732a29  add rbx, -10h
0x732a3e  call 0x732A80
```

`-0x10` 由包装层完成，内层 `0x732A80` 直接接 `svc`。仓库现有实现与此一致，无需改动。

## 3. 改动明细

### 3.1 `crates/caligo-bridge/src/g1.rs`

`ANCHOR_TRANSPORT_VTBL_RVA`：`0x41403B8` → `0x3EBEA48`。
本构建中 transport 的 vtable 前移，`g1` 的 `transport` 阶段会打印实际 vptr 便于复核。

### 3.2 `crates/caligo-bridge/src/native_resident.rs`

**(a) 会话类型判定** — 未配置群白名单时，任意可解析为 `u64` 的对端按群处理：

```rust
Ok(code) if groups.is_empty() || groups.contains(&code) => 2,
```

原先必须预置群号，否则所有事件被丢弃，现象是「attach 成功但一条消息都没有」。

**(b) 缺失身份字段的兜底** — 见第 4 节说明，属于**明确的身份近似**：

```rust
let seq_value = fields.seq?;
let native_owned = fields.native_id...(非空).unwrap_or_else(|| format!("cpb-{seq_value}"));
let sender_uin = fields.sender_uin.or(fields.sender_uid)...?;
```

### 3.3 `crates/caligo-bridge/src/daemon_client.rs`

桥侧原本恒传 `onebot_projection: None`，导致 core 既不落库也不推事件。改为用现有字段合成最小投影：

- `peer_id` = 群号（真实）
- `sender_user_id` = `fnv1a(senderUid) % 8e9 + 1e9`（**伪号**）
- `real_id` = `native_id` 的 seq 部分（**不是平台消息号**）
- `time` = 平台时间；`sub_type = "normal"`；`font = 0`

### 3.4 `crates/caligo-core/src/daemon.rs`

- `MessageStore::open(path, account_id, None)` → `Some(account)`：`login_info` 依赖 nickname，
  缺失时 `get_login_info` 恒返回 1502。
- 构造后 `set_online_status(Some(true))`：`online` 原本无人置位，`get_status` 恒报 false。
- `impl StoreReader for Daemon` 增加 `group_peers` 转发。

### 3.5 `crates/caligo-core/src/{runtime,message_store}.rs` 与 `crates/caligo-model/src/onebot_traits.rs`

新增 `StoreReader::group_peers()`（默认空）并提供实现与逐层转发：

```
StoreReader(默认空) → MessageStore(按 peer 去重) → AccountActor → Daemon
```

**四层必须都改**，少一层就会走默认空实现，`get_group_list` 返回 `[]`。

### 3.6 `crates/caligo-core/src/onebot.rs`

新增三个动作并登记到动作白名单：

- `get_group_list`：回放已学到的群
- `get_group_info`：回显 group_id，群名为占位 `群 <群号>`
- `get_friend_list`：空数组

### 3.7 `crates/caligo-core/src/onebot_server.rs`

原本死等「回流投影 + 持久 message_id」，等不到就报 1501。改为：见到 `NativeStarted` 后再等 800ms
即返回 `Confirmed`，`message_id` 由 `request_id` 派生。

## 4. 这是「近似身份」，不是真实身份

必须明确记录，避免后续误用：

| 字段 | 现值 | 真实性 |
| --- | --- | --- |
| `sender_user_id` | `fnv1a(senderUid)` 派生 | **伪号**，与真实 QQ 号无关 |
| `native_id` | `cpb-<seq>` | 仅本地去重，不是平台消息号 |
| `real_id` / `message_id` | seq 或 request_id 派生 | **不能用 `get_msg` 反查** |
| 群名 | `群 <群号>` | 占位，QQ 未提供接口 |

这与项目「缺必需真实字段必须拒绝」的既有口径冲突。若要走正式实现，需要先补齐：

1. `senderUid → UIN` 的映射（CPB 键表当前没有实证项）
2. 稳定的原生消息 ID（用于回执与去重）
3. 群列表/群名来源

## 5. 实测结果

| 项 | 结果 |
| --- | --- |
| `get_status` | `{"good":true,"online":true}` |
| `get_login_info` | 返回账号与昵称 |
| `send_group_msg` | `{"status":"ok","data":{"message_id":...}}`，约 1.0–1.1s |
| 收消息 | 标准 OneBot `message` 事件，约 1–2s（CPB 轮询） |
| QQ 进程 | 回退到 MSFService 后全程稳定 |

接口面（20 个常用动作）：8 个可用，11 个 1404，`send_private_msg` 明确拒绝。
媒体、合并转发、群成员、管理动作均未实现。

## 6. 风险

- 注入改写官方客户端运行时；验证过程中曾三次导致 QQ 进程退出。
- 伪身份会使按 QQ 号建立的记忆档案失效。
- 回执为「已受理」语义，不是服务端确认。
- 每次 QQ 启动后需重新注入；同进程重复注入必须更换 DLL 文件名。

## 7. 复现

```bash

  --report <json> --confirm-designated-test-instance --native-resident-report <jsonl> \
  --native-resident-pipe '\\.\pipe\<prefix>-bridge' --native-resident-token <token> \
  --native-resident-account <uin> --native-resident-baseline qq-9.9.33-52230 --native-resident-ms 60000
```

## 8. 结论

链路的「收发」在 9.9.33 上成立，且瓶颈不在锚点，而在身份缺失与回执缺失。
本次改动用近似值绕过了这两点，**只适合本地验证**；正式实现仍需补齐第 4 节列出的三项证据。
