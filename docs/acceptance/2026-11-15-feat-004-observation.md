# feat-004 回调线程与停止观测合同（2026-11-15）

本合同是后续取证的判定设计，不是现场准入，也不是验收通过。适用正式 wrapper 的固定 QQ 9.9.36-53644；固定映像摘要、已有现场和限制见 [progress](../../progress.md#current-state)。历史 G3 的 consumer ABI/线程/寿命是独立路线，不能用 wrapper 结果代替。

## 分层与判定

| 观察 | 能证明 | 不能证明 |
|---|---|---|
| 停止中直接调用 listener 的合成探针 | 测试输入下 stopped 分支没有修改受检接收状态；异常和缺记录分别为失败或 unknown | QQ 确曾在停止后调用、真实 payload 的全部行为、QQ 内部注销或排空 |
| JS listener 或 Promise handler 入口上的当前 OS TID，配合同代次与关联事件 | 该次 JS 回调执行时的线程；只能用于所记录事件 | QQ native 生产者线程、其他 callback 的线程或最终 owner |
| native callback 入口的线程与对象关联 | 仅在入口身份、固定 hash、对象/请求关联和捕获机制均独立证明时，证明对应样本的 native 入口线程 | 全部回调都在该线程、最终释放或全局 quiescence |
| 停止后正常退出、端口关闭 | 指定代次的管理端和 owner 已关闭 | listener 键必定移除、既有快照消失、宿主 drain 或可热卸载 |
| 停止后真实关联迟到回调被观察且状态保持不变 | 指定事件和代次的停止隔离 | 所有在途事件均已到达，或以后不会有回调 |

`listener_armed` / owner pump 的线程、主动调用的合成回调及轮询时线程均不能标成 QQ native callback 线程。缺失日志不是没有回调的证明。有限观察窗口内没有事件只记 unknown。停止前后记录必须区分时间顺序、事件来源与同一进程代次；不能用正文、时间相似性冒充请求身份。

## 2026-11-15 请求级诊断实现（离线）

research 模式为每个已登记文本请求分配 JS 环境中本监听器代次内的临时正整数；各阶段携带相同序号，poll 保留代次号与不完整标记。队列达到 32 项、序号耗尽或代次持久化失败时标记不完整；后续 poll 重置该批的溢出标记。白名单过滤只输出有界代次、序号和固定阶段，不输出账户、正文、cookie 或原始请求/消息 ID。普通模式不启用该诊断；测试仅验证实现和模拟交错。

代次号只在同一 JS 环境且内部计数未被外部改写时有意义，必须另以进程代次和环境证据限定；临时序号没有独立映射时不能识别真实用户请求。报告上限为进程内 32 次，整批日志未写出、缺失或截断仍为 unknown，不能推断未发生；该字段也不证明 QQ native callback OS 线程或全局 drain。旧标签数组的历史记录不能追溯出请求序号。新实现在固定版本完成了单次私聊阶段采集；正式线程与寿命验收仍独立开放。

## 离线日志解析

可用 `node scripts/analyze-text-send-trace.mjs <本机阶段日志>` 只读解析当前固定标签格式。工具只输出有界代次、临时序号和白名单阶段；格式异常、超限、明确溢出或无轨迹返回 unknown，不打印原始内容。`scope: unverified` 与 `completeness: unknown` 始终保留：即使标签完整，也须单独证明进程、JS 环境、实际请求关联以及报告未缺失；工具不会证明 callback OS 线程、对端收取或全局 drain。真实日志继续留在 ignored `local-evidence/`，禁止作为公开测试夹具。

## 并发发送轨迹的关联限制

本轮修复前的 `textSendTrace` 是 listener 代次共用的固定标签数组，不包含请求身份，poll 后清空，单次数组最多 32 项。`sanitize_text_send_trace` 只保留标签；跨 poll、并发、截断或缺失时，不能从标签顺序推断单个请求的事件顺序，也不能用 `sendResults` 的键给无键标签补关联。此前限定为一次发送的样本只在其当时准入和零其他请求等记录成立时可按单请求解释；本次复现没有否定该样本的其他独立证据。

离线 VM 使用实际 `build_send_js` 生成的两个不同请求，分别以先一后二和先二后一的顺序完成 Promise；两个输出阶段数组完全相同，且两条 `sendResults` 各自为 accepted。另一个 11 请求样本产生 33 个阶段，数组只保留 32 项且无截断标记，丢失一个 submit_return。实验只证明当前诊断无法区分这两种交错及无法从输出识别该丢失，不证明账本混淆或现场线程。可重跑材料与 hash 见 [progress](../../progress.md#current-state)。

请求级诊断必须让每个阶段携带本监听器代次内有界且不复用的临时关联序号，在登记前分配、由同一 pending 对象贯穿回调；不得输出账号、正文、cookie、原始 request ID 或 native ID。需要定义跨 poll、并发、容量溢出、重复/旧代次和缺失记录的明确 unknown 语义，证明序号不会影响投递和账本。日志中的序号没有独立映射时仍不能与具体用户请求关联；须另有经审查的本地关联证据。线程观测另需独立采集机制，不能把阶段记录线程当作 native callback 线程。此段为设计约束，不能视为现场许可。

## 2026-11-18 JS 入口 OS 线程观察（已实现，现场待验）

research 构建在 listener 注册前安装五个无参原生观察函数，由接收、add、update、文本发送 Promise 和精确回读 Promise 的 JS handler 入口同步调用。函数忽略 `FunctionCallbackInfo`，不读取消息或返回值布局，只在预分配原子槽写入事件种类、当前 Windows OS TID 与临时保留序号。owner 轮询或停止时再写本机报告。该 TID 是对应 JS 入口的执行线程；报告行本身的 `tid` 仍是写报告的 owner，二者不能混淆。

安装额外绑定 QQNT.dll SHA-256 `75B19E58A123B0513E99DF4DF3EBC6524478535BA44651024D6A20821F5086E5`、三个具名导出及精确 RVA。`Function::New` 与 `Context::Global` 的 Local 返回，以及 `Object::CreateDataProperty` 的 `Maybe<bool>` 均按该映像的隐藏返回缓冲区 ABI 调用。观察地址发布前以 `FROM_ADDRESS | PIN` 固定 bridge 至进程退出。只有所有函数安装成功且五个函数完整时 listener 才捕获观察器；安装失败单独记录为 unavailable，不能用部分记录声称通过。

每进程最多 128 次保留机会，超限/槽满以一次 `capture_incomplete` 标记；未 drain、缺日志和采集失败仍为 unknown。保留序号不是请求 ID 或回调发生顺序，槽位扫描输出顺序也不是事件时间顺序。记录明确为 `association=unverified source=js_entry`，不得以相邻记录或正文时间给它补请求关联。旧 listener 保留其原闭包；停止合成探针期间禁止采样，不能将合成输入标为真实 QQ 事件。

此实现与自建 Windows 线程/Node VM 测试只能证明实现和测试输入合同。真实线程样本须新 QQ 代次重新准入，独立核对零其他发送或对应关联证据、固定构建、listener 与请求轨迹；发送需对应目标与单次正文授权。既有 QQ 样本未运行本观察器。该方案不采系统 ETW/LBR，也不证明 native 生产者线程、停止后实际迟到回调、最终 owner 或全局 drain；未证寿命继续不热卸载。

2026-11-18 现场补充：新 QQ62780 在固定构建的单次私聊中完成发送、账本回读、八阶段轨迹和用户单条确认；观察器实际记录 add/update/promise/readback 及两条 recv 的 JS 执行 TID 均为2440，与 owner 相同。原始记录未含请求身份，不能因同轮单次发送就给每条线程记录补请求关联；序号也不证明发生顺序。正常停止通过而真实迟到/最终释放/drain 仍 unknown，证据与 SHA-256 见 [progress](../../progress.md#current-state)。此前“现场待验”为实现检查点，本条仅补指定样本的实际 JS 线程证据。

## 2026-11-18 本地停止的结果持有合同

正式 QQ owner 的最后一次通知交接之后，仍可能由精确回读产生结果；worker 收到本地停止标志后不保证继续消费它。owner handle 已关闭、worker 线程结束均不能作为结果已得到 core ACK 的证明。正式入口额外持有 resident 根，仅在 worker 已结束且 resident 没有待交出/待 ACK 结果或真实未决预留时释放。停止期限内不能证明时返回 `ERR_SHUTDOWN_PENDING_RESULTS`（`0x22`），报告 `shutdown_results`，保留 resident；CLI 明确返回失败，不触发新发送或热卸载。

这是一项本进程内持有与失败报告合同：未确认结果仍可供后续经过独立设计的恢复处理，不是磁盘持久化、自动 worker 重启、任意异常恢复或 QQ 全局 drain。自建夹具中的显式 ACK 仅证明本地释放条件，不授权生产端伪造 ACK；宿主退出仍会结束内存寿命。对已 ACK unknown 的迟到窗口预留，需要区分其容量与未确认结果，关闭后不能仅凭该已确认占位永久误报未收尾。锁中毒、owner/native 清理异常等不由正常停止样本自动覆盖。

同一轮还收紧精确回读的对象寿命：启动查询与成功/失败回调均要求 `R.sends[key]` 仍是捕获的 pending，公共终结函数同样检查 stopped/current/done；退休或替换后的旧完成不能重建结果、覆盖新结果或启动过期查询。尚在保留窗口内的迟到强身份仍可更正。离线正反回归与最终构建范围见 [progress](../../progress.md#current-state)，既有 QQ 现场来自本次修复前构建，不据此提升状态。

## 2026-11-18 owner Rust hook 异常边界

owner pump 是不可展开的 `extern C` 回调。普通tick和停止hook都在 Rust 内的窄 `catch_unwind` 边界调用，hook锁的guard留在边界外；发生Rust unwind或检测到hook锁中毒即锁存本宿主代次的故障、quarantine并请求worker停止。后续hook执行、替换/清空及相关owner操作须拒绝，原hook捕获和独立resident根保留，shutdown返回 `ERR_OWNER_HOOK_FAULT=0x23`，CLI报失败。保留panic payload以避免其析构再次panic；锁存后不重复执行hook，故不随tick无界积累。

这只约束当前实现的Rust unwind路径，不捕获SEH/访问冲突、panic=abort、panic hook自身终止进程、二次析构panic或原生未定义行为。不因捕获成功恢复使用可能已损坏的resident，也不调用未知原生清理来伪造释放。单独子进程使用fake QQNT与实际pump回调复现旧版normal/stop panic导致进程abort，再验证修复后的存活、非零停止、sticky quarantine和Weak根保留；锁中毒也以独立子进程测试。正常成功/超时/未ACK停止对照继续通过。执行结果见 [progress](../../progress.md#current-state)；未在真实QQ制造panic。

## 2026-11-18 正式 owner 清理失败传播

正式停止使用同一个 `close_daemon_owner` 路径撤权查询并调用resident.close。listener移除等清理返回Err时，不得仅写日志后让pump关闭并释放根；应锁存独立cleanup故障、quarantine并保留捕获根，停止后续hook和原生清理，shutdown返回 `ERR_OWNER_CLEANUP_FAILED=0x24`。此分支与Rust unwind的0x23区分，CLI明确报告清理未完成；不自动重试未证幂等的原生移除。

| 本地停止结果 | 已证明的含义 | 根与后续行为 |
|---|---|---|
| 0 | 自有pump关闭、worker结束且本地结果满足收尾判定 | 可释放该本地根；不证明QQ全局drain |
| 0x22 | 本地结果或worker收尾未确认 | 独立resident根保留，不重发 |
| 0x23 | Rust hook unwind或hook锁中毒 | sticky quarantine，原hook捕获保留，不再执行 |
| 0x24 | 正式owner清理返回Err | sticky quarantine，保留原根，不重复原生清理 |

对应LAB必须调用正式入口共享的清理路径与实际pump/export，使用自建HostAdapter返回listener移除错误，核对非零结果、Weak根存活、一次清理和后续无调用；正常对照仍应完成关闭并释放。它不证明真实QQ已发生该错误、服务已注销、未决回调已消失或允许热卸载。执行状态以 [progress](../../progress.md#current-state) 为准。

## 2026-11-18 自有 pump wake/close 准入合同

bootstrap的ready保留用于拒绝同代次重新接入，不能再单独作为wake句柄可用证明。普通EntryHandle::wake和worker蹦床唤醒必须共用独立准入，与close_req、quarantine、关闭开始/完成状态一起判断；关闭或隔离后不得向旧handle再次uv_async_send。ordinary wake不得获取DRAIN_HOOK锁，否则hook内唤醒可造成重入死锁。

自有wake准入序列化只覆盖uv_async_send的调用生存期：关闭请求先禁止新的普通wake，等待已准入调用返回，第一轮停止请求可提交唯一关闭唤醒，owner在该顺序之后才能调用一次uv_close。锁顺序为hook→wake，无wake→hook；不在持有wake锁时等待owner执行或跨uv_close回调。重复shutdown/pump不得再次关闭同一handle。

确定性LAB以fake QQNT实际wake/pump/export和屏障控制在途send，验证关闭后两API拒绝、并发关闭等待在途send且阻止新准入、hook内唤醒无死锁及一次uv_close；故障路径继续保根。该顺序依赖uv_async_send只投递工作而不在调用栈内同步执行pump；fake也不得制造该不真实重入。wait_ms约束关闭确认等待，不提供中断挂起native调用或锁等待的能力。该合同只证明Caligo自有句柄的调用顺序，不证明QQ dispatcher停止或native callback全局静默。实现及验证状态见 [progress](../../progress.md#current-state)。

## 2026-11-19 停止顺序与迟到证据的离线判定

| 桶级冲刷 | `0x1C0A8DA` 返回后继续批次循环。末批续点 `0x1C0A918` 后更新线程缓存字节数（`0x1C0A91D`），再经 `0x1C0A93F` 返回。 | `RSP+0x90` |
| 空缓存补充 | `0x1C0A9A1` 后先判断取出数量。非空时首节点可由 `0x1C0AA0C` 放入返回寄存器，余链非空才在 `0x1C0A9CF` 接入缓存。正常返回点是 `0x1C0AA1A`。 | `RSP+0x70` |
| 缓存清理 | `0x1C0AF7D` 仅表示扫桶完成。随后才执行元数据摘链、活动计数和预算更新，并在 `0x1C0AFFC` 将缓存元数据放回复用链。解锁后经 `0x1C0B019` 返回。 | 共享归还入口沿桶级冲刷、扫桶、清理逐层核对后为 `RSP+0x110` |

以上偏移仅适用于核对过的正常调用链。每层须先对上栈中的调用续点。`0xBC3098` 和 `0x1C0ACA8` 的叶函数尾跳保留上游返回槽。`0xBC34D1`、`0x1C0AF6A`、`0xBC13D4` 在尾跳前恢复本帧，再继承上游槽。匹配须以同一线程、实际返回槽及所指续点为准。使用子调用入口算得的返回槽后，还须在上游实际续点校验返回后的栈指针。间接调用实际目标未知、帧处于未覆盖的序言或展开路径、或者返回漏采时，外层完成保持 unknown。

自建宿主在两次尾跳前后读取实际栈指针和槽内续点，绑定线程、块、分配代次和释放序号，再在同一帧核验实际返回。四槽仍保留实际接收者和弱零入口。36 组观察开关对照中，144 条尾调用链满足同槽和实际返回，宿主寿命计数一致。9 种坏记录均拒绝错误匹配，包括相同续点串到旧代次，以及仅有尾调用记录却缺少实际返回。

重新验证 45 份先前自建宿主轨迹。嵌套冲刷返回时移交序号已变、缓存仍未关闭。外层清理返回后才观察到关闭，移交序号与冲刷返回时相同。每轮分别删去内层返回、删去外层返回或只抹去目标代次的独立移交序号，共 27 份缺证对照，目标代次均保持 unknown。保留返回但缺序号的对照仍能确认其他有完整证据的代次。

固定 QQ 只完成静态路径核验。真实外层执行、跨线程覆盖、异常退出和独立代次移交仍待证。缓存元数据复用的返回只覆盖该次清理，实际对象终止释放与全局静默仍需各自证据。 [复跑入口与结果](../../progress.md#current-state)

#### 四槽轮换中的同类重入与异常退出

2026-11-20 在自建 Windows x64 进程以实际硬件执行断点验证四槽轮换。两槽观察宿主的分派和弱零标记，一槽在移交入口与外层续点之间轮换，第四槽记录调用方边界。观察器仅启动同一个自建可执行文件的子进程。宿主另行记录提交序号和内外层真实返回地址，观察开关的宿主记录一致。

| 场景 | 实际观测与判定 |
|---|---|
| 同一续点重入 | 切换到外层续点后漏掉内层入口。内层返回碰到同一续点，但栈指针属于更深的帧，8 次均被拒绝配对。随后能核对外层返回，内层缺证的窗口仍为 unknown。 |
| 不同续点重入 | 宿主独立记录证实内层续点不同，轮换槽漏掉内层入口和返回。8 次均只收到外层返回，而独立提交序号增加两次。回放删掉内层的分派和弱零标记后，仍能凭序号缺口保留 unknown。 |
| 提交前或提交后异常退出 | 两种情形均收到 Windows 首次异常通知，原外层正常续点均未触发。调用方边界确认已离开原帧后清除待匹配记录。提交后异常虽有一次序号递增，原窗口仍为 unknown。后来 16 次同地址同栈槽的正常调用通过独立新代次和新调用序号核验。 |
| 内层异常被捕获 | 外层随后正常返回且提交序号只增加一次，已观察到的异常仍使该窗口保持 unknown。缺独立提交序号的正常调用同样保持 unknown。 |

7 种条件各 8 轮，共 56 组观察开关对照，另有 7 种坏记录回放。证据范围是单工作线程的自建宿主。真实 QQ 尚未证实有等价的调用方边界或独立移交序号，现有四槽轮换也无法完整采集上述重入。其原生移交和释放继续保留 unknown。 [复跑入口与结果](../../progress.md#current-state)

#### 固定镜像的异常清理与移交凭据

2026-11-20 在同一 SHA-256 固定镜像上追加 77 项断言。共享归还和一条直接归还路径的 C++ 异常状态表共指向三个清理函数。共享归还的正常路径和异常清理都通过该帧保存的锁对象调用同一个解锁函数。按节点归还的分支还可在内部临时解锁，处理后重新加锁。因此只观察到解锁，无法区分正常完成、异常清理或仍在执行的子步骤。

所选桶级冲刷、补充、扫桶、缓存清理及共享取出的五个函数各有栈展开描述，其记录标志均为零，未携带本函数自己的异常处理入口。展开描述给出栈恢复规则。判断此次调用是否真的退出原帧，仍需绑定同一线程、同一调用和展开后的实际边界。共享批次数、共享空闲节点数及所查 span 内已分配计数均有增减路径。在所查路径内没有证实能独立记录物件移交顺序或采集缺口的凭据。

复核了 56 份同类重入与异常退出轨迹，以及 11 份缓存转移轨迹。16 对反例包含两组各 8 对。第一组分别删去正常调用的返回和提交后异常退出的异常回执，两者留下相同的记录，包括相同的提交序号和调用方边界。第二组删去不同续点重入的内层辅助标记，并隐藏独立序号，单次提交与漏采内层提交留下相同的记录。两组的受影响代次均为 unknown，随后有完整证据的新代次仍可独立确认。缓存往返的回放也确认仅凭边界快照和已知分配通知无法识别漏采。

当前结论限于固定镜像的所查路径及自建宿主归档回放。真实 QQ 中的原帧退出边界、独立移交凭据及跨线程覆盖仍待证。 [复跑入口与结果](../../progress.md#current-state)

微软 [StartTraceW 文档](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-starttracew)建议使用能说明组件用途的稳定会话名，避免以随机名堆积跟踪会话；该建议与识别本次实际所有权是不同问题。会话名、GUID 或运行前的无冲突检查本身均不能证明所有权；遇到已存在会话不得仅凭同名停止，需独立核实后按合同处理。不得将进程内私有会话的观察外推为系统会话可以用相同方式安全恢复。

### 无事件的具名系统会话尝试

自建脚本配置描述性名称、非内核默认 GUID、system logger 与有界内存缓冲；`EnableFlags=0`，不配置 provider、文件、PMC、LBR 或 QQ。当前未提升 token 调用 `StartTraceW` 返回 `ERROR_ACCESS_DENIED`（5），没有取得句柄，因此没有调用 query/stop。四个模拟后端测试覆盖权限拒绝、同名冲突、成功且持有句柄和成功但句柄为空；前两者不得停止任何会话。实际系统会话的启动成功、同名冲突、按句柄清理及崩溃残留均未验证；权限允许也不自动满足此前的会话所有权、隐私、采集及恢复门。[StartTraceW 错误与权限说明](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-starttracew)及本机脚本/结果 hash 见 [progress](../../progress.md#current-state)。

### 存活控制器的工作进程退出对照

自建控制进程持有真实无 provider 的 in-process private ETW 会话句柄，并启动不接触 ETW 的独立子进程。正常退出、非零退出和超时后终止三个样本中，控制进程在子进程启动前及结束后均成功查询，最终按自己取得的句柄停止会话。证据和脚本 hash 见 [progress](../../progress.md#current-state)。这些样本仅验证控制器仍存活时的私有会话清理，不证明控制器自身崩溃、系统 logger 代次或外部恢复者的权限/所有权；也不验证工作进程的数据采集。

若真实系统控制器发生崩溃或启动回执丢失，会话是否存活及其归属均为 unknown；恢复者不得只凭名称、GUID、PID 或过期句柄停止。可审计方案仍需定义能够核验的会话身份与代次、受保护的交接证据、冲突和句柄复用的拒绝条件以及无法判定时的人为处置；以上私有对照不能满足这些条件。[ControlTraceW](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-controltracew) 另指出 stop 返回 `ERROR_MORE_DATA` 时停止可能已经发生，不能将非零结果一律视为仍在运行并盲目重试。

### 私有会话过期句柄的 ABA 对照

在本机同一自建进程中对无 provider、无文件的 private in-process 会话做 3 组各 12 次对照：A 正常停止后创建 B，B 分别使用相同名称/GUID、相同名称不同 GUID、不同名称及不同 GUID。三组中 B 均 12/12 取得与 A 相同的句柄数值，使用 A 的过期数值和 A 的查询参数执行只读 query 在 B 存在时均返回 0。第三组在 B 创建前额外查询过期数值，12/12 返回 4201；B 创建后又 12/12 返回 0。A、B 均为本进程自建，停止仅使用当次成功创建的当前句柄，从未用过期值 stop。

这在指定私有会话和本机 Windows 上直接展示句柄数值复用及过期值查询的 ABA：只验证数值相同或 query 成功不能证明当前对象仍是原代次，也不能证明查询时输入的旧 GUID 被用作代次校验。它不证明系统 logger 或跨进程句柄采用相同规则；对其恢复仍应保持 unknown，直到独立建立可核验的所有权与原子性。实验源码、按组结果和逐项只读核对 hash 见 [progress](../../progress.md#current-state)。

后续仅以同一进程的私有会话核对 query 输出：A 停止后 B 使用不同名称及 GUID 时，旧句柄 query 输出的名称和 GUID 均为 B（12/12），可据此发现这一组替换；B 复用 A 的名称和 GUID 时，旧句柄 query 输出均与 A 的名称和 GUID 相同（12/12），无法凭这两个字段区分代次。两组句柄数值均复用，实际 stop 仅使用本次成功创建的当前句柄。此检查不比较所有返回字段，也不是 query 与 stop 之间的原子锁；样本不证明系统日志或跨进程行为。完整输出只读审计及负例见 [progress](../../progress.md#current-state)。

2026-11-16 补充：在同一自建进程的 20 次同名同 GUID 私有会话替换中，逐项比较 `EVENT_TRACE_PROPERTIES`、嵌套 `WNODE_HEADER` 的具名成员及返回名称共 25 项；A 的两次查询、B 的查询及用 A 旧值查询 B 的上述字段均相同，句柄数值均复用。只保存字段差异而非原始指针；停止仅使用当次创建的当前句柄。这些对照说明指定样本的已比较字段无法区分代次，不比较填充字节或 ETW 完整状态，也不证明系统 logger 无代次机制。查询与后续停止依旧不是已证的原子操作；系统会话恢复方案不能将匹配的字段快照提升为所有权证明。
